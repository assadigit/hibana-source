- ROOT CAUSE, read from the code and then PROVEN LIVE against hibana.ir with the real account (throwaway, self-cleaning): the pull engine and the island share ONE api.Client; the engine's §8 cheap-poll seeds an If-None-Match for every board path it mirrors — /api/projects?sort=recent AND /api/projects/:id/devboard, the EXACT strings the island fetches — and the client's get() attaches the stored validator to EVERY GET. LIVE PROOF: projects GET 200 W/"5muwzo" → conditional 304 → fresh 200 (4646B, 7 projects); the second project's devboard GET 200 W/"vkzsh6" → conditional 304 → fresh 200 (full payload, the Currena board loads). The WEB island never sees this (its fetches ride cache:'no-store', which never conditional-polls — the shim's 304 support was speculative; the island never sends If-None-Match, grep-proven). The first board worked because it RACED the engine's first pull round and won the validator-less window; a later cold boot could bite the first board the same way if the island lost that race.
- THE FIX (hibana-desktop v0.1.4, commit c586dbd + annotated tag v0.1.4-desktop → CI → release live): the bridge is the INTERACTIVE transport — internal/api gains RequestFresh (GETs send NO If-None-Match; a 200 still refreshes the stored validator via absorb so the engine's NEXT poll stays the cheap 304 instead of double-pulling; writes byte-identical to Request — Origin stamp, no blind retry; an unexpected 304 — RFC 9110 §15.4.5 allows 304 only for conditional requests — errors loudly, never a body-less ok). internal/ui: the bridge's Request rides RequestFresh; the ErrNotModified branch is GONE from the bridge; StatusErrors through the bridge log 'hibana bridge: METHOD path → status' so future dogfood reports read straight from data/logs/hibana.log. The ENGINE keeps Request everywhere (§8/§10 unchanged; cmd/acceptance's live-304 proof still asserts the conditional contract).
- TESTS: TestRequestFreshNeverConditional (engine pull seeds → engine re-poll stays ErrNotModified → the fresh GET on the SAME path is the full 200 → the next engine poll is still cheap), TestRequestFreshRejectsUnexpected304, TestRequestFreshWritesStillStampOrigin (T6), and the bridge-level end-to-end regression TestBridgeFreshAfterEngineSeededETag — the exact dogfood scenario: engine seeds the shared client → engine re-poll 304s → the bridge GET on the same path returns 200 + body, twice.
